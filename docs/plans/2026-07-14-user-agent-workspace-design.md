# 面向用户的 Agent 工作区设计

## 目标

将当前“交互验证台”重构为面向最终用户的任务交互页面。页面首先帮助用户表达任务、附加资料、理解执行状态并消费结果；模型路由、事件协议和原始 JSON 继续保留，但只在用户主动打开运行详情后渐进披露。

同时完成已确认的 Langfuse 会话归组：一次 Harness Session 对应一个 Langfuse Session，多轮 Run 保持独立 Trace。

## 现状与问题

- 首页使用“交互验证台”“运行详情”“协议与原始事件”等内部产品语言，默认身份仍然像开发调试工具。
- 空状态的主信息很少，大片留白没有帮助用户判断 Agent 能做什么、怎样开始、何时需要人工确认。
- 快捷任务只是三条并列文本，缺少任务类型、输入预期和结果价值的区分。
- 执行进度已经可以折叠成一行，但与输入框和回答之间的关系不够明确。
- 右侧详情面板对开发者很有用，但空状态占据大量空间；移动端呈现更像调试抽屉而不是用户可理解的“本次运行”。
- 样式表中同时存在旧版自定义 UI 选择器和 assistant-ui React UI 覆盖层，容易导致状态之间的视觉差异和维护负担。
- 当前 Trace 能在 API、Worker 和 Runtime 间传播，但 Harness `session_id` 尚未映射到 Langfuse Session。

## 方案选择

### 方案 A：保留 assistant-ui，重构信息架构与视觉层级（采用）

保留 AG-UI、assistant-ui Thread、Composer、附件、消息动作和现有运行事件模型。重写页面文案、欢迎区、页头、执行条和运行详情的用户层级，并清理冲突样式。

优点是不会重复实现聊天、附件、分支、复制、朗读等基础能力；后端协议不变，风险和迁移成本最低。

### 方案 B：增加左侧会话和 Agent 导航

形成左侧会话列表、中间任务、右侧运行详情的三栏工作台。它需要持久化会话列表、标题、搜索和 Agent 选择接口，超出当前页面重构所需的数据契约。

### 方案 C：只做主题美化

仅调整颜色、字体和间距，无法解决“验证页面”定位、空状态信息架构和开发信息默认暴露的问题。

## 用户体验设计

### 页面身份

- 英文眉题使用 `Agent Workspace`，主标题使用“智能任务助手”。
- 页面不再出现“验证台”“开发者信息”等默认文案。
- 主操作保留“新任务”；运行详情入口改为“本次运行”，表达用户价值而不是技术实现。
- 仅当用户打开“本次运行”后，才显示模型、Provider、耗时、成本、工具和子 Agent。
- 原始协议与事件放在详情底部的“高级诊断”折叠区。

### 欢迎区

欢迎区使用自定义 `ThreadWelcome`，仍由 assistant-ui 的空线程状态和 Suggestion primitive 驱动。

内容层级：

1. 明确提问：“今天想让 Agent 完成什么？”
2. 简短说明：可以分析资料、处理文件、拆解复杂任务，受保护操作会先请求确认。
3. 三个任务卡：
   - 分析与规划：分析仓库或复杂问题，给出带优先级的行动方案。
   - 阅读与整理：读取附件，提取事实、证据和结构化摘要。
   - 执行与协作：调用工具或子 Agent 完成多步骤任务。
4. 可信边界：文件在隔离工作区处理，关键操作需要批准。

卡片仍会直接发送预置 Prompt，不引入新的首页状态。

### 对话与执行

- 对话正文继续使用 assistant-ui Message、Markdown、代码、表格、附件、复制、重试、朗读和反馈能力。
- 消息最大宽度保持适合阅读的约 920px；文本正文控制在更窄的阅读宽度，代码和结构化结果可使用完整消息宽度。
- Composer 保持页面底部，使用更明确的占位文案“描述你希望完成的任务，可附加文件或资料…”。
- 运行时 Composer 上方显示一行执行条：状态、当前动作、工具数、子任务数和耗时。
- 执行条默认折叠，展开后显示工具与子 Agent；成功结束后降低视觉权重，但不隐藏。
- 等待审批时使用暖色并将审批卡作为主要行动，不把批准动作放入开发详情面板。

### 本次运行

- 桌面宽屏：右侧 360px 面板。
- 窄屏：底部面板，最大高度约 72dvh，具有遮罩和清晰关闭按钮。
- 空状态缩短为一句说明，不长期占据屏幕。
- 正常状态依次展示：运行状态、模型与耗时等摘要、工具/子任务计数、用户可读时间线。
- `run_id`、`thread_id`、原始 Harness Activity 只在“高级诊断”中显示。

## 视觉方向

- 采用温和的自然纸张色、深墨绿和少量琥珀色状态色，避免大面积纯白验证页面的空洞感。
- 保留现有品牌色，但增加浅层背景、内容分区和边界，形成明确的页面纵深。
- 字体继续使用系统可用字体栈，不引入远程字体依赖。
- 卡片不过度圆角；使用 8–12px 圆角、1px 边框和克制阴影。
- 所有状态不仅依赖颜色，同时保留文字和图形标记。
- 遵循 `prefers-reduced-motion`，移动端触控目标不小于 40px。

## Langfuse 数据流

```text
AG-UI Thread
  -> Harness Session (session_id)
     -> Langfuse Session (langfuse.session.id)
        -> Run 1 / Trace 1
        -> Run 2 / Trace 2
        -> Run N / Trace N
```

- `RunService.create` 在 API Trace 已存在时给当前 Span 添加 `langfuse.session.id`。
- Worker 恢复 Run Trace Context 后，为根 Span 和其 Harness 子 Span绑定相同 Session 属性。
- 使用 ContextVar 维护当前观测属性，避免每个工具、Sandbox 和 Runtime 调用点重复传参。
- 不记录原始用户内容、文件内容或凭据；现有脱敏规则继续生效。

## 错误与边界状态

- 会话恢复期间显示轻量骨架，而不是在页面中心只显示一行文字。
- 上传失败继续提供可关闭的错误消息；上传中和已就绪状态保持可见。
- Run 失败时执行条显示简短失败状态，并引导打开“本次运行”；错误详情不直接铺满主对话。
- 本次运行面板没有 Activity 时保持可关闭，不阻塞用户输入。
- 页面不伪造“已连接”“Sandbox 正常”等未从服务端得到的状态。

## 验证策略

- 后端单元/集成测试验证：两个不同 Trace 可以共享同一个 `langfuse.session.id`，同一 Worker Run 的所有 Harness Span 都携带该属性。
- 前端静态和组件测试验证：不再出现验证/开发术语；自定义欢迎区包含三类任务、可信边界和可发送 Suggestion；运行详情使用用户文案；移动断点符合底部面板规则。
- 运行完整 Vitest、Next.js production build、目标 Python 测试、Ruff 和 Pyright。
- 使用本地浏览器在桌面和 390px 窄屏下检查空状态、详情面板、输入区和响应式布局。

## 非目标

- 本轮不增加会话历史列表、登录账户、Agent 商店或多 Agent 选择器。
- 不替换 assistant-ui，不自行实现消息列表、Composer、附件或 Markdown 基础设施。
- 不在首页暴露原始事件流或 Langfuse 链接。
- 不改变 AG-UI 协议和现有审批 API。
